# Plan de trabajo: cobranza preventiva por llamadas con Retell

## 1. Alcance del MVP

La solución permitirá:

1. Importar clientes y obligaciones desde el banco o una fuente simulada.
2. Programar llamadas según reglas configurables.
3. Ejecutar conversaciones mediante un agente de voz de Retell.
4. Consultar información adicional del cliente durante la llamada, únicamente cuando sea necesaria.
5. Consolidar resultados, transcripciones, grabaciones, sentimiento, métricas y auditoría en un panel de control.

El MVP será un **monolito modular**, no un conjunto de microservicios: una aplicación web, un backend, un trabajador de llamadas, PostgreSQL y almacenamiento de archivos. Es suficiente para la hackathon y permite separar servicios posteriormente si el volumen lo exige.

---

## 2. Viabilidad del requisito de consultas al backend

**Sí, el requisito #5 es posible con Retell.**

Al crear una llamada, el backend puede pasar variables específicas mediante `retell_llm_dynamic_variables`. Todos sus valores deben enviarse como texto. Durante la conversación, Retell puede ejecutar **Custom Functions** que llaman endpoints HTTP del backend; la solicitud puede incluir el identificador de la llamada, metadata y la transcripción acumulada hasta ese momento. La respuesta puede convertirse en nuevas variables para continuar la conversación. [Variables dinámicas de Retell](https://docs.retellai.com/build/dynamic-variables) y [Custom Functions](https://docs.retellai.com/build/conversation-flow/custom-function).

### Información inicial recomendada

```json
{
  "customer_ref": "cus_01J...",
  "preferred_name": "María",
  "next_due_date": "2026-09-20",
  "language": "es",
  "timezone": "America/El_Salvador"
}
```

El teléfono se envía como `to_number`; no necesita duplicarse como variable.

### Cambio de seguridad recomendado

Aunque el requerimiento propone enviar la fecha de nacimiento al agente, en producción conviene **no incluir la fecha completa en variables dinámicas ni metadata**, porque Retell advierte que esos valores quedan almacenados en texto plano en el registro de la llamada.

El flujo seguro sería:

1. El agente solicita al cliente su fecha de nacimiento.
2. Ejecuta `verify_identity(customer_ref, supplied_dob)`.
3. El backend compara el valor con la fecha cifrada.
4. Devuelve solamente `verified: true/false` y un token corto ligado a esa llamada.
5. Solo con ese token se permite consultar reprogramación, seguros u otros datos.

La fecha, números de cuenta, saldo detallado y datos del seguro permanecen en el backend.

## 3. Arquitectura propuesta

```text
Base del banco / CSV / fake data
              │
              ▼
     API de importación y validación
              │
              ▼
          PostgreSQL
              │
       ┌──────┴────────┐
       ▼               ▼
Programador        Backend/API ───────────► Panel web
de llamadas             ▲
       │                 │ Custom Functions
       ▼                 │
Worker ─────────────► Retell ─────────────► Cliente
                         │
                         │ Webhooks
                         ▼
               Registro de llamadas
                         │
          Grabaciones / logs / transcripciones
```

### Componentes

- **Backend:** reglas, programación, identidad, opciones de asistencia, webhooks y API del panel.
- **Worker:** reclama trabajos pendientes, valida reglas y solicita a Retell la llamada.
- **PostgreSQL:** fuente operativa del panel, historial y auditoría.
- **Almacenamiento de objetos:** grabaciones, transcripciones exportadas y logs.
- **Retell Conversation Flow:** conversación controlada por nodos, funciones y bifurcaciones.

Retell ofrece nodos de conversación, funciones determinísticas y bifurcaciones condicionales, apropiados para separar verificación, recordatorio, asistencia y escalamiento. [Conversation Flow](https://docs.retellai.com/build/conversation-flow/overview).

## 4. Flujo de llamada

1. **Apertura y transparencia**
   - Presentar entidad y propósito general.
   - Informar que se interactúa con un asistente automatizado.
   - Aplicar el aviso de grabación exigido por la jurisdicción.

2. **Verificación**
   - Confirmar que habla la persona correcta.
   - Verificar fecha de nacimiento contra el backend.
   - No revelar información financiera antes de verificar.

3. **Recordatorio preventivo**
   - Comunicar fecha próxima de pago.
   - Confirmar comprensión y disposición de pago.
   - Evitar lenguaje de presión o amenazas.

4. **Asistencia**
   - Si existe dificultad, consultar opciones de reprogramación y seguros.
   - Registrar intención, solicitud de reprogramación o necesidad de atención humana.
   - Una reprogramación es una solicitud pendiente hasta que el backend la valide.

5. **Cierre**
   - Resumir los acuerdos.
   - Confirmar siguiente paso.
   - Registrar exclusión, devolución de llamada o transferencia cuando corresponda.

### Resultado de negocio de la llamada

No se debe equiparar “llamada conectada” con “llamada exitosa”. Para este sistema:

> **Llamada preventiva exitosa:** se verificó a la persona correcta y se comunicó el recordatorio de manera comprensible, o se canalizó correctamente una necesidad de asistencia.

Correo de voz, número ocupado o llamada contestada por un tercero no cuentan como éxito preventivo.

## 5. Sentimiento y adaptación del agente

### Durante la llamada

Después de las primeras dos intervenciones del cliente, el flujo determinará un estado:

- `calm_positive`
- `neutral`
- `confused_anxious`
- `frustrated`
- `distressed`

Para el MVP, el propio modelo puede inferirlo mediante instrucciones y guardarlo como variable. Para mayor trazabilidad, se puede introducir una función `assess_live_sentiment`; Retell enviará a la función la transcripción acumulada y recibirá `label`, `confidence` y `recommended_style`.

| Sentimiento estimado | Adaptación |
|---|---|
| Positivo o calmado | Mensaje breve y directo |
| Neutral | Flujo estándar |
| Confundido o ansioso | Ritmo más lento, explicación simple y confirmaciones |
| Frustrado | Reconocer molestia, evitar repetición y ofrecer ayuda humana |
| Angustiado | Detener presión, ofrecer devolución de llamada o transferencia |

La adaptación puede cambiar tono, velocidad y extensión, pero **nunca** modificar políticas, elegibilidad o información financiera.

### Después de la llamada

Retell proporciona análisis posterior con resumen, `user_sentiment`, `call_successful` y datos personalizados. También pueden extraerse `sentiment_start`, `sentiment_end`, `sentiment_shift`, motivo de tensión y necesidad de intervención humana. [Post-Call Analysis](https://docs.retellai.com/features/post-call-analysis-overview).

En la API actual debe utilizarse `post_call_analysis_data`, incluyendo los presets `call_summary`, `call_successful` y `user_sentiment`; los campos antiguos de prompts fueron retirados el 15 de junio de 2026. [Aviso de migración de Retell](https://docs.retellai.com/deprecation-notice/2026/06-15_legacy_list_endpoints).

El panel debe presentar este dato como **sentimiento estimado por IA**, no como una afirmación objetiva sobre el cliente.

## 6. Panel de control

### 6.1 Resumen ejecutivo

- Llamadas programadas, intentadas, conectadas y exitosas.
- Embudo: conexión → persona correcta → recordatorio entregado → compromiso.
- Pagos puntuales y comparación con un grupo de control.
- Distribución y evolución del sentimiento.
- Alertas de cumplimiento, fallos técnicos y campañas detenidas.

### 6.2 Operación y campañas

- Calendario y cola de llamadas.
- Resultados por campaña, horario, producto y segmento.
- Intentos pendientes, reintentos y llamadas agotadas.
- Capacidad concurrente y ritmo de marcación.
- Pausar, reanudar o cerrar una campaña.

### 6.3 Perfil del cliente

- Datos de contacto parcialmente enmascarados.
- Obligaciones y próximas fechas de pago.
- Historial cronológico de intentos y conversaciones.
- Compromisos, reprogramaciones, seguros y devoluciones de llamada.
- Tendencia del sentimiento y exclusiones de contacto.

### 6.4 Detalle de llamada

- Estado, duración, causa de desconexión y resultado.
- Reproductor de grabación con permisos.
- Transcripción sincronizada y llamadas a herramientas.
- Sentimiento inicial, final y por momento relevante.
- Latencia, errores, costos, logs y versión del agente.

Retell expone transcripción con marcas de tiempo, invocaciones de herramientas, grabación normal o multicanal, logs públicos, latencias y causa de desconexión. [Get Call API](https://docs.retellai.com/api-references/get-call).

### 6.5 Parametrización y auditoría

- Reglas de campaña con borrador, publicación y versionado.
- Horarios, frecuencia, feriados, correo de voz y escalamiento.
- Política de retención y acceso a grabaciones.
- Usuarios, roles y permisos.
- Registro de quién cambió cada regla y cuándo.

## 7. Métricas recomendadas

### 7.1 Embudo preventivo

| Métrica | Fórmula |
|---|---|
| Ejecución programada | trabajos ejecutados / trabajos programados |
| Tasa de conexión | llamadas conectadas / intentos |
| Contacto con persona correcta — RPC | clientes verificados / intentos |
| Entrega efectiva del recordatorio | recordatorios comunicados / clientes verificados |
| Pago puntual | obligaciones pagadas en fecha / obligaciones elegibles |

El impacto principal debería medirse como **incremento de pago puntual frente a un grupo de control**, no solamente como volumen de llamadas.

### 7.2 Efectividad de cobranza preventiva

| Métrica | Definición |
|---|---|
| Intención de pago | clientes que confirman intención / recordatorios entregados |
| Compromiso cumplido | pagos realizados según compromiso / compromisos |
| Resolución en primer contacto | casos resueltos en la primera conversación verificada |
| Reprogramación válida | solicitudes aprobadas / solicitudes realizadas |
| Recuperación por reintento | contactos obtenidos después del primer intento |

### 7.3 Operación y experiencia

| Métrica | Definición |
|---|---|
| Duración promedio — AHT | duración total / llamadas conectadas |
| Transferencia humana | transferencias / llamadas conectadas |
| Distribución de resultados | contestada, buzón, ocupado, sin respuesta, error |
| Cambio de sentimiento | sentimiento final menos sentimiento inicial |
| Exclusión o queja | solicitudes de no llamar y quejas / contactos verificados |

Ocupación, nivel de servicio y abandono solo aplican si existe una cola de agentes humanos; no deben copiarse directamente al agente automatizado.

### 7.4 Calidad técnica y costo

| Métrica | Uso |
|---|---|
| Latencia E2E p50/p95/p99 | naturalidad de la conversación |
| ASR, LLM, TTS, red y base de conocimiento | localizar el componente lento |
| Latencia y error de herramientas | calidad de consultas al backend |
| Integridad de evidencia | llamadas con webhook, transcripción y grabación completas |
| Costo por RPC y por cuenta protegida | eficiencia financiera |

Retell entrega estadísticas de latencia para `e2e`, `asr`, `llm`, `llm_websocket_network_rtt`, `tts`, `knowledge_base` y `s2s`, además del costo y uso de tokens. [Métricas de llamada de Retell](https://docs.retellai.com/api-references/get-call).

## 8. Reglas de negocio parametrizables

### Elegibilidad

- Días antes del vencimiento en que se incluye una obligación.
- Productos, segmentos y niveles de riesgo habilitados.
- Exclusión por pago ya realizado, disputa, mora o dato incompleto.
- Consentimiento de contacto y lista “no llamar”.
- Priorización por fecha, riesgo o monto.

### Horario

- Zona horaria del cliente.
- Ventanas permitidas por día de semana.
- Feriados y fechas bloqueadas.
- Horario preferido del cliente.
- Ventana de seguridad antes del cierre diario.

### Frecuencia y reintentos

- Máximo de intentos por ciclo de pago.
- Separación mínima entre intentos.
- Reintento según resultado: ocupado, sin respuesta o buzón.
- Suspensión inmediata después de contacto exitoso o exclusión.
- Límite de llamadas concurrentes y por segundo.

### Mensajería y privacidad

- Mensaje de apertura y aviso de grabación.
- Información permitida antes de verificar identidad.
- Mensaje genérico de correo de voz, sin detalles financieros.
- Idioma y pronunciación.
- Retención y redacción de datos personales.

### Asistencia y escalamiento

- Condiciones para ofrecer reprogramación.
- Seguros o beneficios consultables.
- Límites que requieren aprobación humana.
- Sentimientos o frases que activan transferencia.
- Horarios y destinos de atención humana.

Las reglas deben publicarse como versiones inmutables. Cada trabajo y llamada conservará la versión utilizada.

```text

                    │
```

### Índices mínimos

- Únicos en `(organization_id, external_ref)` y `retell_call_id`.

- Secuencia en `call_turns(call_id, sequence)`.
- Único en `webhook_events(payload_hash)` para idempotencia.

No se necesita particionamiento para el MVP. Se introduciría por mes únicamente cuando el volumen de llamadas lo justifique.

## 11. APIs principales

| Endpoint | Propósito |
|---|---|
| `POST /api/imports/customers` | Importar o actualizar clientes, contactos y obligaciones |
| `POST /api/retell/webhooks` | Recibir eventos de llamadas de forma idempotente |
| `POST /api/retell/tools/verify-identity` | Verificar identidad y emitir token temporal |
| `POST /api/retell/tools/get-assistance-options` | Obtener reprogramación, seguros o rutas de ayuda |
| `POST /api/retell/tools/request-reschedule` | Registrar una solicitud validada e idempotente |

Retell genera `call_started`, `call_ended` y `call_analyzed`; las llamadas no conectadas todavía producen los dos últimos eventos. Los webhooks tienen reintentos y deben procesarse idempotentemente. [Webhooks de Retell](https://docs.retellai.com/features/webhook-overview).

El backend local debe exponerse mediante un túnel HTTPS durante la demo, porque Retell no llama `localhost` ni direcciones privadas.

## 13. Seguridad y gobierno

1. Verificar `X-Retell-Signature` en herramientas y webhooks.
2. Cifrar teléfono, fecha de nacimiento y referencias sensibles; usar hashes para búsquedas.
3. Aplicar roles de operador, supervisor, auditor y administrador.
4. Versionar reglas, prompts y agente utilizado en cada llamada.
5. Definir consentimiento, retención y transferencia humana con el área legal del país aplicable.

Se recomienda `everything_except_pii`, redacción configurada y URLs firmadas. Retell permite eliminar PII de transcripciones, grabaciones, logs, metadata y resultados de herramientas. [Configuración de almacenamiento y PII](https://docs.retellai.com/accounts/privacy-disable).

Las URLs firmadas de Retell expiran, normalmente en 24 horas. El panel debe regenerarlas bajo demanda o copiar los artefactos permitidos a almacenamiento cifrado controlado por el banco; guardar únicamente la URL temporal en la base no es suficiente. [URLs seguras de Retell](https://docs.retellai.com/accounts/signed-secure-url).


# Stack tecnológico del MVP

El MVP será **autocontenido**: no consultará APIs, bases de datos, autenticación ni sistemas del banco. Todos los clientes, obligaciones, beneficios y pagos serán sintéticos.

## Aplicación

| Capa | Tecnología |
|---|---|
| Panel | React + TypeScript + Vite + Recharts |
| Backend | Python 3.14 + FastAPI + Pydantic |
| Persistencia | PostgreSQL 17 |
| Acceso a datos | SQLAlchemy 2 + Alembic |
| Voz | API/SDK de Retell + webhooks + Custom Functions |

## Ejecución

| Componente | Tecnología |
|---|---|
| API | Contenedor FastAPI |
| Worker | Proceso Python que consulta llamadas pendientes |
| Panel | Contenedor web que sirve la aplicación React |
| Base de datos | Contenedor PostgreSQL con volumen persistente |
| Acceso de Retell | Cloudflare Tunnel o ngrok con HTTPS |

No se usarán Celery, Redis, SQS ni Kubernetes para el MVP.

## Funcionamiento

```text
Panel React
    │
    ▼
FastAPI ─────────► PostgreSQL con fake data
    ▲                    │
    │                    ▼
    │              Worker de llamadas
    │                    │
    │                    ▼
    └── Túnel HTTPS ◄── Retell ──► Teléfono autorizado
```

El worker y la API usan el mismo código, pero se ejecutan como procesos separados:

```text
api     → recibe solicitudes y webhooks
worker  → busca llamadas pendientes y las envía a Retell
```

## Datos simulados

PostgreSQL incluirá datos sintéticos de:

- Clientes y números de prueba autorizados.
- Obligaciones y próximas fechas de pago.
- Elegibilidad para reprogramación.
- Seguro por desempleo y beneficios simulados.
- Pagos y resultados ficticios para alimentar métricas.

La verificación de identidad comparará la respuesta del cliente contra la fecha de nacimiento ficticia almacenada localmente.

# Instrucciones de despliegue

## 1. Servicios de Docker Compose

El archivo `docker-compose.yml` levantará cuatro servicios:

```text
db       PostgreSQL
api      FastAPI
worker   Programador y ejecutor de llamadas
web      Panel React
```

`api` y `worker` se crean desde el mismo Dockerfile del backend, pero arrancan con comandos diferentes.

## 2. Variables de entorno

Crear `.env` sin incorporarlo al repositorio:

```env
DATABASE_URL=postgresql+psycopg://app:password@db:5432/collections
RETELL_API_KEY=...
RETELL_AGENT_ID=...
RETELL_FROM_NUMBER=...
PUBLIC_BASE_URL=https://url-publica-del-tunel.example
APP_SECRET=...
FAKE_DATA_ONLY=true
RETELL_ALLOWED_TEST_NUMBERS=+503XXXXXXXX
```

`RETELL_ALLOWED_TEST_NUMBERS` impedirá llamar accidentalmente a números no autorizados.

## 3. Inicializar la aplicación

```bash
docker compose build
docker compose up -d db
docker compose run --rm api alembic upgrade head
docker compose run --rm api python -m app.seed
docker compose up -d api worker web
```

El comando `app.seed` cargará los clientes y escenarios ficticios.

## 4. Exponer el backend

Crear un túnel HTTPS hacia FastAPI:

```text
https://mvp-hackathon.example
          │
          ▼
http://localhost:8000
```

Configurar en Retell:

```text
Webhook:
https://mvp-hackathon.example/api/v1/retell/webhooks

Verificación:
https://mvp-hackathon.example/api/v1/retell/tools/verify-identity

Información adicional:
https://mvp-hackathon.example/api/v1/retell/tools/get-assistance-options

Reprogramación:
https://mvp-hackathon.example/api/v1/retell/tools/request-reschedule
```

El backend debe validar la firma enviada por Retell antes de procesar cada solicitud.

## 5. Prueba de despliegue

Comprobar en este orden:

1. El panel abre y muestra clientes ficticios.
2. FastAPI responde en `/health`.
3. Se puede programar una llamada desde el panel.
4. Retell llama únicamente a un teléfono autorizado.
5. El webhook registra resultado, transcripción, sentimiento y grabación.

Para una demostración más estable, el mismo Docker Compose puede ejecutarse en una máquina virtual Linux. PostgreSQL no debe publicar su puerto a Internet; solamente el backend debe ser accesible mediante HTTPS.

## Fuera del MVP

- Integraciones con el banco.

- Conciliación real de pagos.

## Key Learnings:

1. El MVP funcionará completamente con datos sintéticos locales.
2. Retell será el único servicio externo.
3. Docker Compose ejecutará panel, API, worker y PostgreSQL.
4. Una lista permitida evitará llamadas accidentales a números reales.
